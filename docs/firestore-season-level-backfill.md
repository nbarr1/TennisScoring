# Firestore season / division-level backfill investigation

## Investigation summary

The current web pages do not read match, season, division, or user data through a custom API route. They subscribe directly to Firestore from client-side React components through the helpers in `@tennis/firebase-client`.

The user-visible symptom for existing divisions is usually that completed or scheduled matches and standings disappear after the season/division-level filters were added. The UI now filters matches and rankings by `seasonId`, and sometimes by `divisionLevelId`. Older Firestore `matches` and `rankings` documents that only have `divisionId` still exist, but they no longer satisfy those queries.

## Exact UI/data flow

### Matches page

1. `apps/web/app/matches/page.tsx` resolves the signed-in user with `useAuthUser()` and loads the user profile with `useUserProfile(firebaseUser?.uid)`.
2. It resolves the active division with `useActiveDivisionId(firebaseUser.uid, profile.divisionId)`.
3. It computes the default season with `currentSeasonForDate()` and builds season choices with `defaultSeasonOptions()`.
4. It loads division levels through `useDivisionLevels(divisionId)` and filters them to the selected season.
5. It subscribes to `divisionMatchesQuery(divisionId, where("seasonId", "==", selectedSeasonId), ...)` and adds `where("divisionLevelId", "==", activeLevelId)` when a specific level is selected.
6. Snapshot documents are mapped into `Match` objects by spreading `d.data()` and adding the document ID as `id`.
7. The page derives sections by `status` (`in_progress`, `proposed`, `scheduled`, `pending_report`, `completed`, `disputed`, `cancelled`) and sorts scheduled/completed groups by timestamp.
8. `MatchCard` renders `status`, `scheduledAt`, formatted score from `liveScore`, player display names, guest labels, server, and winner.

### Dashboard standings page

1. `apps/web/app/dashboard/page.tsx` follows the same user/profile/active-division/season/level resolution pattern.
2. It calls `useRankings(divisionId, { seasonId: selectedSeasonId, divisionLevelId: activeLevelId })`.
3. `useRankings` subscribes to `rankingsQuery(divisionId, where("seasonId", "==", seasonId), ...)` and adds `where("divisionLevelId", "==", divisionLevelId)` when a level is selected.
4. The standings table renders the returned ranking rows directly: `displayName`, wins/losses, sets, games, and game differential.

### Shared Firestore helpers

* `divisionMatchesQuery` reads the top-level `matches` collection, filters by `divisionId`, and orders by `createdAt desc`.
* `rankingsQuery` reads `divisions/{divisionId}/rankings`, orders by `rank asc`, and accepts extra filters.
* `divisionLevelsCol` reads `divisions/{divisionId}/levels`.
* `divisionMembershipsQuery` reads `divisions/{divisionId}/memberships` filtered by `seasonId` and optionally by `divisionLevelId`.

## Firestore dependency map

### `users/{uid}`

Required by the pages and active-division resolver:

| Field | Type | Required by UI | Notes |
| --- | --- | --- | --- |
| `displayName` | string | Yes | Used in roster/member backfill and player search. |
| `email` | string | Yes | Used for search/admin display. |
| `divisionId` | string | Optional but important | Preferred division context when present and valid. |
| `role` | `player \| division_leader \| admin \| app_developer` | Admin gate | Admin page only permits privileged roles. |
| `availability` | object | Optional | Used in match proposal UI. |

### `divisions/{divisionId}`

| Field | Type | Required by UI | Notes |
| --- | --- | --- | --- |
| `name` | string | Yes | Division selectors/display. |
| `leaderIds` | string[] | Yes | Active-division lookup and security/rules. |
| `playerIds` | string[] | Yes | Active-division lookup and roster repair. |
| `activeSeasonId` | string | Optional | Existing type supports it, but the current matches/dashboard pages compute their default from the current date. |

### `divisions/{divisionId}/levels/{levelId}`

Document ID strategy: human/readable or generated ID. The app treats the Firestore document ID as `DivisionLevel.id`.

Required shape:

```json
{
  "divisionId": "division_123",
  "seasonId": "spring-2026",
  "year": 2026,
  "seasonHalf": "spring",
  "name": "Beginner Singles",
  "skillLevel": "beginner",
  "matchType": "singles",
  "description": "Optional description",
  "rankingsEnabled": true,
  "active": true,
  "sortOrder": 10,
  "createdAt": 1770000000000,
  "updatedAt": 1770000000000
}
```

### `matches/{matchId}`

Document ID strategy: generated by Firestore when matches are proposed/recorded.

Fields the current pages read:

| Field | Type | Required for display/query | Notes |
| --- | --- | --- | --- |
| `divisionId` | string | Yes | Base query filter. |
| `seasonId` | string | Yes for current UI | Must match selected season, e.g. `spring-2026`. |
| `divisionLevelId` | string | Required when filtering by a level | Must be a document ID from `divisions/{divisionId}/levels`. |
| `matchType` | `singles \| doubles` | Optional but expected with levels | Can be inferred from the level for backfill. |
| `status` | match status string | Yes | Drives page sections and badges. |
| `player1Id`, `player2Id` | string | Yes | Used for actions/invites and player history. |
| `playerIds` | string[] | Yes | Used in player match-history queries. |
| `player1Name`, `player2Name` | string | Optional fallback display | UI falls back to `Player 1` / `Player 2` if absent. |
| `player2IsGuest` | boolean | Optional | Adds guest label and skips account linking. |
| `liveScore` | object | Yes for scores | Rendered by score formatting helpers. |
| `winner` | `player1 \| player2` | Completed matches | Renders winner badge/name styling. |
| `createdAt` | number (Unix ms) | Yes for matches list query | `divisionMatchesQuery` orders by `createdAt desc`; Firestore excludes documents where the ordered field is missing. |
| `scheduledAt`, `startedAt`, `completedAt` | number (Unix ms) | Sorting/display | Missing `scheduledAt` renders `Time TBD`; these can be used to repair missing `createdAt`. |

### `divisions/{divisionId}/rankings/{userId}`

Document ID strategy: one ranking row per user per division. The current type stores season and level fields on the row, but if multiple seasons/levels are required concurrently, the app must either maintain separate docs or ensure the row fields match the active filter.

Fields read by standings:

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `userId` | string | Yes | React key and player identity. |
| `displayName` | string | Yes | Rendered as player name. |
| `seasonId` | string | Yes for filtered query | Missing value excludes row. |
| `divisionLevelId` | string | Required when level is selected | Missing value excludes row. |
| `rank`, `matchesWon`, `matchesLost`, `setsWon`, `setsLost`, `gamesWon`, `gamesLost`, `gameDifferential` | number | Yes | Rendered directly. |

### `divisions/{divisionId}/memberships/{seasonId}_{divisionLevelId}_{userId}`

Document ID strategy comes from `divisionMembershipId(seasonId, divisionLevelId, userId)`.

Required shape:

```json
{
  "divisionId": "division_123",
  "seasonId": "spring-2026",
  "divisionLevelId": "beginner-singles",
  "userId": "user_123",
  "displayNameSnapshot": "Alex Player",
  "emailSnapshot": "alex@example.com",
  "phoneSnapshot": "+15555555555",
  "role": "player",
  "status": "active",
  "source": "migration",
  "assignedBy": "script:backfill",
  "createdAt": 1770000000000,
  "updatedAt": 1770000000000
}
```

## Root cause

The page queries now require season-aware and division-level-aware fields. Existing documents that are otherwise valid can be invisible because one or more of these fields are absent, stale, named differently, or have the wrong type:

* `matches/{matchId}.divisionId`
* `matches/{matchId}.seasonId`
* `matches/{matchId}.divisionLevelId`
* `matches/{matchId}.matchType`
* `matches/{matchId}.createdAt` because the matches page orders by this field and Firestore omits documents missing an `orderBy` field
* `matches/{matchId}.playerIds` and side-specific user IDs when older matches were imported by name only
* `divisions/{divisionId}/memberships/{membershipId}` for season/level roster views
* `divisions/{divisionId}/rankings/{rankingId}.seasonId` and `divisionLevelId` for standings

This is a data-shape/backfill issue, not a required frontend redesign. Firestore updates alone should make the matches page show the updated documents. Standings may also require the existing ranking recalculation/repair workflow after matches are updated.

## One-time update tool

Use `scripts/backfill-division-season-level.mjs` for a safe one-time backfill. It:

* Defaults to dry-run mode.
* Validates the division and level documents before writing.
* Validates season IDs (`spring-YYYY` / `fall-YYYY`) and match type.
* Logs every match and membership document that would change.
* Writes a backup/export JSON before mutation.
* Only updates missing `seasonId`/`divisionLevelId` unless `--overwrite-existing` is supplied.
* Discovers roster-linked match documents that are missing `divisionId` by querying `playerIds`, `player1Id`, and `player2Id`, then repairs `divisionId` only when all attached non-guest player IDs belong to the target roster.
* Repairs missing match `createdAt` from `completedAt`, `scheduledAt`, `startedAt`, the Firestore document create time, or the script run timestamp so ordered matches-page queries can include the document.
* Links match side IDs from roster display names when an older completed match was imported by name.
* Upserts season/level membership documents for division roster users and linked match users.
* Uses batched writes and is idempotent; re-running produces no writes once the target fields already match.
* Does not delete any data.

### Dry-run

Preferred invocation in GitHub Codespaces:

```bash
GOOGLE_APPLICATION_CREDENTIALS=/path/to/service-account.json \
  pnpm backfill:season-level \
  --division <divisionId> \
  --season spring-2026 \
  --level <divisionLevelId> \
  --backup-dir "$HOME/firestore-backups"
```

The package script now includes an internal argument separator, and the script skips any additional `--` separators. These are equivalent:

```bash
pnpm backfill:season-level -- \
  --division-id <divisionId> \
  --season-id spring-2026 \
  --division-level-id <divisionLevelId>
```

If `--` or `--division` is reported as unknown and `--help` prints the old `node scripts/backfill-division-season-level.mjs --division-id DIVISION_ID` usage, the Codespace is running an older copy of this script. Pull the latest branch and reinstall before retrying.

### Live update

```bash
GOOGLE_APPLICATION_CREDENTIALS=/path/to/service-account.json \
  pnpm backfill:season-level \
  --division <divisionId> \
  --season spring-2026 \
  --level <divisionLevelId> \
  --backup-dir "$HOME/firestore-backups" \
  --write
```

`--live` is accepted as an alias for `--write` for compatibility with older runbooks. Use `--overwrite-existing` only after reviewing dry-run output and confirming every match in the division should be moved to the target season/level.

## Verification steps

1. Run the dry-run and review the console output plus generated backup JSON. If it reports `0 match document(s)` queued, check the diagnostics line for how many documents already have the target `divisionId` and how many roster-linked documents are missing `divisionId`.
2. Run the live command with `--write` if the planned changes are correct.
3. Open `/matches`, select the target season and division level, and confirm the expected matches now appear.
4. If `/dashboard` has standings but `/matches` is still empty, rerun the dry-run and confirm whether it plans `createdAt` repairs; the matches page query orders by `createdAt`, while standings can be computed from completed matches without that ordering.
5. Open `/dashboard`, select the same filters, and confirm standings. If standings are still empty or stale, run the existing ranking repair/recalculation workflow for that division.
6. No web redeploy is required for data-only Firestore corrections unless you also deploy code changes.

## Risks and assumptions

* The script intentionally does not delete documents or rewrite score data.
* Display-name based user linking assumes roster display names uniquely identify imported historical match names. Review dry-run output before writing.
* The script preserves existing season/level values unless `--overwrite-existing` is passed.
* Existing Firestore security rules affect the web app, but this script uses Firebase Admin credentials and bypasses rules. Restrict service-account access and store backups securely.
* If the rankings data model needs multiple ranking documents per user across seasons/levels, that is a separate schema decision; this tool focuses on making existing match and membership documents match current UI dependencies.
